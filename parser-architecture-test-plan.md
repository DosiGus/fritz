# Test Plan: Parser Architecture

Generated by `/plan-eng-review` on 2026-04-29
Branch: main
Repo: fritz

## Affected Entry Points

- `handle_food_message()` — user-facing food logging path.
- `parse_with_food_intent_v2()` — parser orchestration path.
- deterministic parser — new local simple-food parser.
- OpenAI parser boundary — complex language and fallback behavior.

## Key Interactions To Verify

- `100g Skyr` saves without OpenAI.
- `1 Banane` saves or estimates without OpenAI.
- `250g Skyr, 1 Banane, 30g Whey` saves as a multi-item log without OpenAI.
- `eine Schüssel Haferflocken` still asks to save personal memory, then upgrades the second log.
- `Falafel-Sandwich mit Hummus, Halloumi und Auberginencreme` still uses mocked OpenAI and does not double-count components.
- OpenAI failure falls back to deterministic parse when safe.
- OpenAI failure returns the friendly parser-unavailable message only when no safe deterministic parse exists.
- Template naming state still treats the next message as the template name, not a food log.

## Edge Cases

- `OPENAI_API_KEY` present in developer shell must not make normal tests hit the network.
- Invalid OpenAI JSON/schema returns fallback or friendly error.
- Simple parser must refuse complex composite meals instead of guessing.
- Plural and lowercase simple foods are canonicalized for the beta wedge.
- Meal type facts like `zum Frühstück` are preserved in deterministic parse output.

## Critical Paths

- Simple food log -> deterministic parse -> portion engine -> nutrition matcher -> confidence engine -> saved log.
- Complex food log -> OpenAI parser -> adapter -> validator -> portion engine -> saved/clarify.
- OpenAI unavailable -> deterministic fallback if safe -> saved log.
- OpenAI unavailable + no deterministic parse -> friendly error, no zero-kcal saved log.
